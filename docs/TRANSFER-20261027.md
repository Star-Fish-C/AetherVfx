# AetherVfx 跨电脑开发交接

更新：2026-10-27。仓库：[Star-Fish-C/AetherVfx](https://github.com/Star-Fish-C/AetherVfx)，统一使用 `main`。本文整理产品思路和对话决定，具体证据以仓库现状和下方链接为准。

**当前独立特效播放器没有完成，原生预览因客户端崩溃保持禁用。** 不要把独立面板、托管测试、已创建句柄或非空纹理当作真实粒子画面。用户目前要求先离线开发；准备好可审查的方案后再约定游戏内验证时间。

## 到另一台电脑先做什么

1. 找到本机仓库，检查 `git status --short --branch` 和 `git log -5 --oneline`，保留未提交改动。联网后 `git fetch origin`，核对差异，再安全地同步 `main`；若尚无仓库则克隆。不要直接覆盖本机工作。
2. 检查本机客户端版本、游戏 EXE 指纹、Dalamud、FFXIVClientStructs、Penumbra API、.NET SDK 和实际 SDK 路径。另一台电脑的路径、版本和代理端口不一定相同；遇到网络问题先检查本机代理配置。
3. 阅读本文件和 [旧交接及命令](HANDOFF-20261027.md)，再阅读 [开发环境](DEVELOPMENT.md)、[原生兼容性](NATIVE-COMPATIBILITY.md)、[本机二进制证据](NATIVE-BINARY-20261027.md) 和 [验收记录](ACCEPTANCE.md)。这些文档包含历史记录；测试数量、路径和分支名以最新代码及实际命令结果为准。
4. 在用户同意游戏内验证之前，不启动游戏、原生观察器或探针，不修改游戏安装文件，也不将兼容性门槛直接改成 true。用户不方便一直显示游戏画面，日后约定的验证应尽量短，并说明需要用户进行的操作。

## 用户想要的产品

用户觉得 VFXEditor 的粒子、发射器和时间线操作太复杂，希望有中文、直观的 Dalamud 插件，以**完整特效为图层**，不需要逐粒子编辑。

期望流程：**浏览素材 → 在独立窗口观看 → 加入工作台 → 调整并组合 → 最后选择装备 → 导出 Penumbra PMP**。浏览阶段不应要求装备、改变工程或绑定装备。组合和导出应使用同一编译产物，使位置、旋转、缩放、颜色和循环不会只在预览中生效；最终 PMP 的目标是关闭工作台插件后仍可由 Penumbra 独立加载。

最终独立播放器的用户要求是**空白三维场景、只有真实 VFX、没有可见人物或游戏主画面**，支持相机操作、自动重播和素材／组合切换。可以研究不可见载体及真实骨骼挂点，但不能把截图、主画面裁切或简化动画当作真实独立渲染。资源若依赖特殊目标、骨架或场景，应说明限制。

此前开发交接采用分阶段路线：**0.4 先验证独立视图中的角色与真实 VFX，后续 0.5 再隐藏角色实现空场地**。这是技术验证顺序，最终仍须满足用户无人物的播放器要求，不应把带人物的中间阶段称为最终完成。

工作台还需支持素材搜索、收藏、地区／怪物／副本等可追溯分类、常驻组合图层、独立层变换、工程保存和装备导出。全量目录、预览能力和可编辑能力分别记录；未知路径的资源不能因没有名称或无法编辑而从目录隐藏。用户最终希望通过简单直观的界面完成上述流程。

## 当前实现与实际进度

- 项目标识仍为 0.3.4 开发接续版。仓库有目录、工程、AVFX 编译、装备绑定及 PMP 导出代码；这些代码和文件级测试不等于游戏内完整验收。详情与当前限制见 [README](../README.md) 和 [验收记录](ACCEPTANCE.md)。
- `WindowPreviewAdapter` 只展示停用状态并恢复旧资源映射，**没有接入原生视图、真实 VFX 渲染目标或帧显示**。`NativePreviewSafety.Compatibility` 五项为 false；实验开关不能绕过。自身预览同样受原生保护限制。
- 已知游戏路径素材预览请求会保留原路径，并避免为浏览而强制解析 AVFX；归档素材和编译组合需要资源映射。游戏路径可能被当前 Penumbra Mod 重定向，不保证是原版文件。
- 托管 `PreviewSession` 实现会话代次、资源逆序清理、失败后保留依赖、显式安全重试，以及 Framework 更新时检查的 30 秒单调时钟初始化超时。这些是后端基础，不证明原生所有权或线程安全。
- 最近一次针对本机源码的普通托管测试为 48 项通过，插件构建 0 警告／0 错误；另有 8 项离线分析脚本测试通过。早前使用真实素材做过结构往返、编译与 PMP 文件级检查；它们不替代游戏内视觉、长期运行和 Penumbra 独立加载验收。
- 本机分析 EXE 的版本为 `2026.10.06.0000.0000`，SHA-256 为 `958b78e278ad896493c484eb313ff605ab41edefef74f92b0ee078e69b281bf9`。另一台电脑须重新校验，不能仅按版本号或旧 RVA 假设兼容。

## 崩溃与原生调查结论

2026-10-26 用户报告游戏崩溃。历史记录见 [崩溃报告](2026-10-26_原生预览崩溃-report.md)。本机分析还发现旧实现把 ActorVFX 返回的 `0x1E0` 对象错误当作 `0x390` 的 Scene.VfxObject 使用；相关强转与写入已移除。不要将这一发现当作对整次崩溃全部原因的证明。

当前最大的实际阻碍：尚未证明 CharaView 与游戏共享槽位的独占申请和交还协议、ActorVFX 生命周期及原生销毁线程，也未证明离屏输出包含真实粒子、透明混合和深度。CharaView 初始化会删除指定角色槽中已有对象，空 DrawObject 不等于安全空槽；角色自动分配也不能直接充当视图槽分配器。

已发现一个派生视图沿用基础初始化但覆盖释放；现有观察器只挂基础 Release，可能漏掉该派生释放，不能凭其日志证明所有权或完成清理。离屏引用对象和界面取得的输出指针位于不同索引表；分组数据与输出索引存在候选连接，但粒子完整渲染路径尚未证实。详细地址、扫描范围与限制见 [本机二进制证据](NATIVE-BINARY-20261027.md)。

## 继续开发的方向

优先围绕**能实际显示真实 VFX 的后端**推进，不要长期只补文档、计数或界面外壳：

1. 利用现有离线分析脚本和客户端／依赖源码，继续追踪特效分组到离屏粒子 pass、输出纹理、透明和深度；区别静态证据与运行时推断。
2. 找到可证明的视图资源占用、冲突时交还、原生析构及线程方案；确认角色槽、相机表、引用计数和派生类型的覆盖。若当前路线无法安全实现，应明确诊断并探索其他使用游戏真实渲染管线的方案。
3. 证据足够后实现真实视图、资源加载、相机及会话生命周期；先接游戏路径素材，再接归档映射和编译组合。兼容门槛和构建指纹应基于证据，不能直接修改布尔值冒充支持。
4. 完成离线方案后与用户约时间，按 [验收记录](ACCEPTANCE.md) 分步开展游戏内验证；实际看到角色／真实粒子并满足用户要求后才能声称相应阶段完成。完整验收还包括连续切换、长时间播放、场景切换、释放及 Penumbra 关闭插件后的独立加载。

本机脚本 `scripts/Verify-Development.ps1` 可执行离线构建和测试；`scripts/Inspect-NativePreview.py` 使用 capstone、pefile 进行只读 EXE 分析。使用与该电脑游戏匹配的 SDK 路径，详细参数和版本见 [开发环境](DEVELOPMENT.md)。本机 `artifacts/`、游戏原始资源、PMP、转储及日志不在 GitHub；在新电脑重新生成，不要上传这些内容或任何凭据。
